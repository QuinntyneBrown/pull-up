## Behavior

`RequestEmailChange`: the authenticated user submits `newEmail` + `currentPassword`. The handler verifies the password (failure → `InvalidCredentialsException` → 401), generates a 256-bit raw token + HMAC hash, stashes pending state on `User`, persists, and dispatches the verification email via `IEmailSender`. Returns 202. The primary `Email` stays unchanged until confirmation.

`ConfirmEmailChange`: the authenticated user submits the raw token. Handler hashes it, calls `user.TryConfirmEmailChange(hash, now)` — the domain method promotes `PendingEmail` to `Email` only if the supplied hash matches the stored hash and the token has not expired. On failure → `InvalidEmailChangeTokenException` → 400 with a generic body so the endpoint cannot be probed.

Both commands are audited (`USER_EMAIL_CHANGE_REQUESTED`, `USER_EMAIL_CHANGE_CONFIRMED`).
