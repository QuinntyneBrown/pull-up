## Behavior in plain English

`AuditingBehavior` wraps every MediatR request. If the request type carries `[AuditedAction("X")]`, the behavior generates a correlation id, runs the inner handler, and writes one `AuditLogEntry` row with `Event="X"` and `Outcome="SUCCESS"`. If the inner handler throws, the catch block writes the same row with `Outcome="FAILURE"` and rethrows. Audit writes use a **fresh** DbContext scope via `IServiceScopeFactory` so the handler's partial state (un-saved entity additions, etc.) is not flushed to the database when we record the FAILURE row.

The first annotated command is `RegisterUserCommand` (slice BT-024, already shipped in MB1). Subsequent BI1 slices that touch security-sensitive operations (BT-006 sign-in, BT-009 sign-out, BT-010/011 password reset, BT-015 account delete, plus any role-change endpoint) will add their own `[AuditedAction(...)]` markers — the table from L2-060 is the canonical list.

### One test fix during implementation

The first run of `AuditingTests` failed against SQLite with `NotSupportedException: SQLite does not support expressions of type 'DateTimeOffset' in ORDER BY clauses`. The query was `db.AuditLog.OrderByDescending(a => a.OccurredAt).FirstOrDefaultAsync()`. Resolution: switched the success test to `.ToListAsync()` followed by client-side `OrderByDescending`, and the failure test to `.AnyAsync()`. This is a **test-only** SQLite quirk; the production SQL Server provider handles `DateTimeOffset` ordering natively, so the L2-061 retention query and any future audit-list endpoints can ORDER BY freely.
