# BI1 — BT-019 + BT-018 cancel: notification dispatcher + cancel-event

This eval covers two paired BT slices that landed together because the cancel handler dispatches notifications via the new infrastructure.

## BT-019 — DispatchInvitationNotification + INotificationSender

- **L2 IDs:** L2-028, L2-030, L2-037.
- **Files added:**
  - `Application/Abstractions/NotificationKind.cs` — enum: `EventInvited`, `EventUpdated`, `EventCancelled`, `EventReminder`, `RsvpChanged`.
  - `Application/Abstractions/INotificationSender.cs` — single `SendAsync` method.
  - `Infrastructure/Notifications/LoggingNotificationSender.cs` — MVP no-op logger per BP1 §9.
  - `Application/Features/Notifications/DispatchInvitationNotification/{Command,Handler}.cs` — wraps a single per-recipient dispatch with per-user preference gating (defaults to all-on when no row exists).
- **Files edited:** `Infrastructure/DependencyInjection.cs` — registered `INotificationSender → LoggingNotificationSender` singleton.

### Behavior

The dispatcher reads the recipient's `NotificationPreference` (defaults all-on if missing) and gates by kind: `EventInvited`/`Updated`/`Cancelled` ride `NewInvitations`; `EventReminder` rides `EventReminders`; `RsvpChanged` rides `RsvpChanges`. If the flag is on, the call reaches `INotificationSender.SendAsync`. The dispatcher is intentionally per-recipient — calling sites loop and dispatch one at a time so per-user gating is honored without batching.

- **L2 IDs:** L2-029, L2-030, plus L2-027 (host-only).
- **Files added:**
