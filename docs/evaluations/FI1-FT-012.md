# FI1 — FT-012 Notification preferences toggles

## What shipped

- `ProfilePageComponent` extended:
  - Three `mat-slide-toggle`s in a "Notifications" section bound to a reactive `prefsForm` (`newInvitations` / `eventReminders` / `rsvpChanges`), defaulting all-on.
  - `ngOnInit` calls `profile.getNotificationPreferences()`; the response seeds the form with `setValue(prefs, { emitEvent: false })` (so the initial population doesn't trigger a re-save) and flips `prefsLoaded` to `true`.
  - `prefsForm.valueChanges` is piped through `debounceTime(400)` + `takeUntilDestroyed(destroyRef)`; whenever the form is loaded (post-seed) it calls `profile.updateNotificationPreferences(value)`. Snackbar on save failure.
- Template + SCSS updated to include the new "Notifications" section card.

## Acceptance test (Playwright POM)

- `e2e/notification-preferences.spec.ts` — 1 scenario × 2 projects = **2 tests**, all passing.

The test:
1. Seeds the access token; stubs `GET /api/users/me` and the prefs endpoints (`GET` returns the test-side `prefs` object; `PUT` mutates it).
2. Asserts the three inner `<button role="switch">` elements each have `aria-checked="true"` (all-on default).
3. Clicks "Event reminders"; waits for the **debounced PUT** to land.
4. Reloads the page; asserts that `event-reminders` is now off and the other two remain on — confirming the toggle persisted server-side.

Result:

```
2 passed (9.6s)
```

## Note

The Playwright assertion targets `mat-slide-toggle > button[role="switch"]` (where Angular Material renders the actual switch element) for `aria-checked` rather than the host `<mat-slide-toggle>` wrapper. Recorded so future spec writers don't repeat the dead-end at the host-element level.
