# FI1 — FT-011 Profile page (view + edit)

## What shipped

- `projects/domain/src/lib/profile-page/profile-page.component.{ts,html,scss}` — `pu-profile-page`. Composes `AppBarComponent`, `NavRailComponent` (≥768px), and `BottomNavBarComponent` (<768px). Loads the current user via `auth.loadCurrentUser()` on init. Renders the M3 `mat-form-field` triple (full name / display name / email read-only) with `mat-hint` on the email field explaining the confirm-link flow. Has an "Edit profile" button.
- `projects/domain/src/lib/profile-page/edit-profile-dialog.component.{ts,html,scss}` — `pu-edit-profile-dialog`, opened via `MatDialog`. Reactive form (`fullName`, `displayName`) seeded from current values; on save returns `EditProfileDialogResult` to the parent.
- `ProfilePageComponent.openEdit()` opens the dialog, then on result calls `profile.updateProfile(...)` → `auth.loadCurrentUser()` (via `switchMap`) so the page reflects the new values without a manual refresh. Snackbar on success and on failure.
- `app.routes.ts` — added `/profile` route, protected by `authGuard`.
- `domain/src/public-api.ts` — exports `ProfilePageComponent`.

## Acceptance test (Playwright POM)

- `e2e/pages/profile-page.ts` — `ProfilePagePom` with read-only field locators + edit-dialog locators.
- `e2e/profile-edit-flow.spec.ts` — 1 scenario × 2 projects = **2 tests**, all passing.

The test:

4. Loads `/profile`, asserts the three read-only fields match.
5. Clicks "Edit", changes the names, saves.
6. Asserts the page now shows the new values (page re-fetched `/api/users/me` and rendered the mutated state).
