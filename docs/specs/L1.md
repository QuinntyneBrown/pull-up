# L1 — High-Level Requirements

The Pull Up application must let families and close friends create, share, and respond to small social events with as little friction as possible. The requirements below state what the system must do, not how. Detailed behavior lives in `L2.md`; every L1 has at least one L2.

## L1-001: Account registration
A new person must be able to create a Pull Up account using a full name, email address, and password, and immediately reach the authenticated app after registration.

## L1-002: Sign-in and session management
Existing users must be able to sign in with email and password, remain signed in across page reloads via a securely-stored token, and sign out explicitly.

## L1-003: Password reset
A user who has forgotten their password must be able to request a reset and complete the reset from an emailed link without contacting support.

## L1-004: Profile management
Each user must be able to view and edit their full name, display name, and email, and view metadata about their account (last password change, app version).

## L1-005: Account deletion
A user must be able to delete their own account from the profile screen; deletion must remove their personal data and cancel their participation in future events.

## L1-006: Notification preferences
Each user must be able to toggle which notifications they receive: new invitations, event reminders, and RSVP changes for events they host.

## L1-007: Event creation
A signed-in user must be able to create an event with a title, date, time, location, optional description, and an initial list of invitees. The event must be persisted and visible in the host's event list immediately.

## L1-008: Event viewing
A signed-in user must be able to view a list of their upcoming and past events grouped by time period (this week, later this month, next month, past), and open any event to see its full details (title, date/time, location, description, host, and guest list).

## L1-009: Event editing
The host of an event must be able to edit its title, date, time, location, description, options (allow +1, show guest list), and invitee list before the event date.

## L1-010: Event cancellation
The host of an event must be able to cancel/delete the event, which notifies invitees and removes the event from active listings.

## L1-011: Guest invitation management
A host must be able to add and remove invitees on an event, and invite people who are not yet Pull Up users by email address.

## L1-012: RSVP
An invitee must be able to set their RSVP for an event to one of `Going`, `Maybe`, or `Can't go`, and change it any time before the event date. RSVPs must update aggregate counts on the event detail view.

## L1-013: Event notifications delivery
The system must deliver notifications according to user preferences: a notification when a user is invited to a new event, a reminder 24 hours before each event the user is attending, and a notification to the host when an invitee's RSVP changes.

## L1-014: Authentication security
The system must protect user credentials and sessions: passwords stored only as salted hashes from a modern password-hashing function, JWT access tokens signed and validated on every request, repeated failed sign-ins rate-limited and audit-logged.

## L1-015: Authorization (RBAC)
Access to operations must be enforced from database to UI through a role-based access control model: at minimum a `User` role for normal account holders and a `Admin` role for system administrators. Authorization rules must prevent a user from acting on an event they neither host nor are invited to.

## L1-016: Input validation and output safety
Every command that mutates state must be validated server-side before any persistence occurs; clients must surface validation errors as actionable feedback in the originating UI. All user-supplied content rendered in the UI must be safely encoded so it cannot execute as markup or script.

## L1-017: Data protection
All network traffic between client and server must be encrypted in transit (HTTPS); credentials and personally identifying information must be protected at rest in the database (hashed passwords; encrypted columns or DB-level encryption for PII where applicable); secrets must never be logged.

## L1-018: Responsive UI
Every authenticated and unauthenticated screen must function and look correct across XS (<576px), SM (≥576px), MD (≥768px), LG (≥992px), and XL (≥1200px) viewport widths, mobile-first.

## L1-019: Accessibility
The UI must be operable by keyboard, expose semantic structure via ARIA where native semantics are insufficient, and meet WCAG 2.1 AA color contrast for body text and interactive elements.

## L1-020: Performance
Interactive operations must feel instant: 95th-percentile event-list load under 1.0s on a warm cache, 99th-percentile API response under 500ms for read operations and under 1000ms for write operations under normal load.

## L1-021: Audit logging
Security-sensitive events (sign-in success and failure, password reset request and completion, account deletion, role changes, event deletion) must be recorded to a tamper-resistant audit log with a timestamp, actor, and outcome, retained for at least 90 days.

## L1-022: Empty and error states
Every list-bearing screen must render an empty state when its data set is empty and an error state when the data fetch fails, each with a clear path forward for the user.

## L1-023: Production operability
The deployed system must expose readiness and liveness health checks, structured application logs, and a documented one-command local-startup path so a fresh clone can run the full stack without out-of-band setup beyond the documented prerequisites.

## L1-024: Dependency hygiene
The build pipeline must surface known-vulnerable third-party packages on both the .NET and Angular sides so dependency risks cannot ship to production unnoticed.
