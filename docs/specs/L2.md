# L2 — Detailed Requirements

Every L2 traces to one L1 in `L1.md` and includes Given/When/Then acceptance criteria specific enough for a developer to write a Playwright POM acceptance test (frontend) or an xUnit/MediatR integration test (backend) without further clarification. Responsive behavior is included on every UI-facing L2.

---

## L2-001: Account registration with valid input
**Traces to:** L1-001

A first-time user must be able to create an account from `/sign-up` with full name, email, and password, and land on the authenticated home with a session in place.

**Acceptance Criteria:**
1. Given the sign-up page, when the user submits a full name (≥1 char), a syntactically valid email (RFC 5322 simple), and a password meeting the complexity rule in L2-003, then the system creates a `User` row with a salted password hash, issues a JWT access token, and navigates to the authenticated home page.
2. Given a viewport width <576px, when the registration form is rendered, then all fields and the primary button occupy 100% of the available form width and stack vertically with ≥48dp tap targets.
3. Given a viewport width ≥768px, when the registration form is rendered, then the auth card is centered horizontally with a max-width of 440px and the page background extends to the viewport edges.

---

## L2-002: Registration rejects duplicate email
**Traces to:** L1-001

The system must not allow two accounts to share an email.

**Acceptance Criteria:**
1. Given an existing user with email `x@example.com`, when a sign-up request is submitted with the same email, then the API returns HTTP 409 with a `code=DUPLICATE_EMAIL` problem detail and no new `User` row is created.
2. Given the sign-up page, when the API responds with `DUPLICATE_EMAIL`, then the form surfaces "An account with this email already exists" as field-level error text under the email input and the password input remains untouched.

---

## L2-003: Password complexity at registration and reset
**Traces to:** L1-001, L1-003

Passwords must meet a minimum complexity rule consistent across registration and password reset.

**Acceptance Criteria:**
1. Given a sign-up or password-reset submission, when the password contains fewer than 8 characters, or zero digits, or zero non-alphanumeric symbols, then the API rejects the request with HTTP 400 and the client renders "At least 8 characters, one number, one symbol." under the password field.
2. Given a password that meets all three complexity rules, when the submission is otherwise valid, then the operation proceeds.

---

## L2-004: Sign-in with valid credentials
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given an existing user, when sign-in is submitted with the correct email and password, then the API returns HTTP 200 with a signed JWT access token, a refresh token, and the user profile, and the client navigates to the home page.
2. Given any viewport width, when sign-in succeeds, then the URL becomes `/home` and the previously visited unauthenticated page is replaced in browser history so back-navigation does not return to `/sign-in`.

---

## L2-005: Sign-in with invalid credentials
**Traces to:** L1-002, L1-014, L1-021

**Acceptance Criteria:**
1. Given an existing user, when sign-in is submitted with an incorrect password, then the API returns HTTP 401 with a generic "Invalid email or password" body that does not reveal whether the email exists.
2. Given an invalid sign-in attempt, when the response returns, then an audit log entry is written with the email attempted, a redacted IP/user agent fingerprint, the timestamp, and `outcome=FAILURE`.

---

## L2-006: Session persistence across reload
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given an authenticated session, when the browser reloads any authenticated page, then the user remains signed in for at least 14 days from the last sign-in or refresh, without re-entering the password.
2. Given the access token has expired but the refresh token has not, when the client makes an API call, then the client transparently exchanges the refresh token for a new access token and retries the original request once.

---

## L2-007: Sign-out clears session
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given an authenticated session, when the user activates "Sign out" on the profile screen, then the client clears its stored tokens, invalidates the refresh token server-side, and navigates to `/sign-in`.
2. Given a signed-out state, when the user activates browser-back to a previously authenticated route, then the route guard redirects them to `/sign-in` rather than showing stale content.

---

## L2-008: Request password reset link
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given the password-reset page, when the user submits any syntactically valid email, then the API returns HTTP 202 with no body and the client shows "If an account exists for that email, a reset link is on its way." regardless of whether the email matches an account.
2. Given a submitted email that matches a real user, when the reset is requested, then the system records a `PasswordResetToken` with a 256-bit cryptographically-random value, a 60-minute expiry, and an unused flag, and sends an email containing a link to `/password-reset?token=<value>`.

---

## L2-009: Complete password reset
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given an unused, unexpired reset token, when the user submits a new password meeting L2-003, then the API marks the token used, updates the user's password hash, invalidates all existing refresh tokens for that user, and returns HTTP 200.
2. Given an already-used or expired token, when the reset is submitted, then the API returns HTTP 400 with `code=INVALID_TOKEN` and no password is changed.

---

## L2-010: Password reset audit log entry
**Traces to:** L1-003, L1-021

**Acceptance Criteria:**
1. Given a password reset request, when the API issues a reset token, then an audit log entry is written with the user id, timestamp, and `event=PASSWORD_RESET_REQUESTED`.
2. Given a successful password reset completion, when the password is changed, then an audit log entry is written with the user id, timestamp, and `event=PASSWORD_RESET_COMPLETED`.

---

## L2-011: View own profile
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a signed-in user, when they navigate to `/profile`, then the page renders the avatar (initials from full name), full name, email, last-password-change relative date, display name, and the version banner.
2. Given a viewport width <768px, when the profile page is rendered, then the bottom nav bar is visible with "Profile" highlighted; given a viewport ≥768px, the left nav rail is visible with "Profile" highlighted instead.

---

## L2-012: Edit display name and full name
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a profile-edit form, when the user submits a full name of 1–100 characters and a display name of 1–40 characters, then the API persists the change and the profile screen refreshes with the new values without a full reload.
2. Given a submission with an empty full name or a name >100 chars, when the request is sent, then the API returns HTTP 400 with field-level errors mapped to the originating field.

---

## L2-013: Change email triggers verification
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a profile-edit form, when the user changes their email and confirms with their password, then the system stores the new email as `pending_email`, sends a verification link to the new address, and the displayed email remains the previous one until verified.
2. Given a click on the verification link within 24 hours, when the verification endpoint is hit, then `pending_email` becomes the primary email and the change is reflected on the profile.

---

## L2-014: Account deletion confirmation flow
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given the profile page, when the user activates "Delete account", then a dialog requests confirmation and the user must re-enter their password to proceed.
2. Given a confirmed delete with the correct password, when submitted, then the API returns HTTP 204, the client clears all tokens, and the user is navigated to `/sign-in` with a "Your account has been deleted" snackbar.

---

## L2-015: Account deletion data effects
**Traces to:** L1-005, L1-017

**Acceptance Criteria:**
1. Given a confirmed delete, when processed, then the user's profile fields (full name, display name, email, password hash, avatar) are removed or replaced with `[deleted user]` tombstone values, the user's hosted future events are cancelled, and the user is removed from invitee lists on future events.
2. Given a deleted account, when an invitee on a past event views the past event detail, then the deleted user appears as `[deleted user]` rather than with their previous identifying information.

---

## L2-016: Toggle notification preferences
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given the profile page Notifications section, when the user toggles "New invitations", "Event reminders", or "RSVP changes", then the API persists the change immediately (debounced ≤500ms) and the toggle reflects the persisted state.
2. Given a viewport <576px, when the Notifications section renders, then each setting row stacks the icon, title, supporting text, and toggle in a 56px+ tap row; ≥768px the toggle sits flush-right with the supporting text on a single line.

---

## L2-017: Default notification preferences
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given a freshly registered user, when they first reach the profile screen, then all three notification toggles are `On` by default.

---

## L2-018: Create event with required fields
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given the New Event form, when the user submits title (1–120 chars), date (today or later), time (HH:MM), location (1–200 chars), and an optional description (0–2000 chars), then the API creates an `Event` row owned by the user, persists the initial invitee list, and returns HTTP 201 with the new event id.
2. Given a successful creation, when the user is returned to the home page, then the new event appears in the appropriate time-grouped section.

---

## L2-019: Create event with no invitees
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given the New Event form, when the user submits without adding invitees, then the event is created with the host as the sole participant and a host-only RSVP of `Going` is recorded.

---

## L2-020: Event date and time validation
**Traces to:** L1-007, L1-016

**Acceptance Criteria:**
1. Given a create or edit request, when the submitted date is in the past relative to the server's clock, then the API rejects with HTTP 400 `code=PAST_DATE` and the client renders "Event date must be today or later." under the Date field.
2. Given a submitted time that is not a valid HH:MM, when the request is sent, then the API rejects with HTTP 400 `code=INVALID_TIME`.

---

## L2-021: Field length validation on event fields
**Traces to:** L1-007, L1-016

**Acceptance Criteria:**
1. Given the New Event form, when any field exceeds its max length (title 120, location 200, description 2000), then the client prevents submission and shows "Maximum N characters" supporting text.
2. Given a field at exactly its max length, when submitted, then the event is created successfully.

---

## L2-022: Home page event list groupings
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given a user with events spanning multiple weeks, when the home page loads, then events appear under section headers "This week", "Later this month", "Next month", and "Past" based on the event's local date relative to today.
2. Given a viewport <576px, when the home page renders, then each event card spans 100% width with the date block at left, title and meta stacked at right; ≥992px the event cards remain single-column but with comfortable horizontal padding inside a centered 1200px container.

---

## L2-023: Event detail content
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given a tap on an event row, when the event detail page loads, then it renders the date (full weekday and date), the title, time range, location, description, host (name + relationship + invite send date), and a guest panel with going/maybe/can't-go counts and a list of guests with their per-guest contributions.
2. Given the current user is invited but not host, when the detail renders, then the page shows a "Your RSVP" segmented control with the current state selected; given the current user is host, the page additionally shows host actions (edit, cancel).

## L2-024: Past events accessible via filter

**Acceptance Criteria:**
1. Given the home page with at least one past event in the user's history, when the user selects the "Past" filter chip, then the list re-queries scoped to past events and renders them in reverse chronological order grouped by month.

## L2-025: Filter chips behavior

**Traces to:** L1-010, L1-013

**Traces to:** L1-013

**Acceptance Criteria:**

## L2-038: 24-hour reminder
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given an invitee with `Event reminders` preference on and an `RSVP=Going` or `Maybe` on a future event, when the system clock reaches exactly 24 hours (±5 minutes) before the event's start time, then a reminder notification is delivered referencing the event title, time, and location.

---

## L2-039: RSVP change notifies host
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given a host with `RSVP changes` preference on, when any invitee on their event creates or modifies an RSVP, then a notification is delivered to the host naming the invitee and the new RSVP state.

---

## L2-040: Password hashing function
**Traces to:** L1-014, L1-017

**Acceptance Criteria:**
1. Given an account is created or its password is changed, when the password is persisted, then the stored value is the output of Argon2id (memory ≥64 MiB, parallelism ≥2, iterations tuned to ≥100 ms on production hardware) or PBKDF2 with ≥600000 iterations and SHA-256 or bcrypt with cost ≥12; the password itself is never stored.
2. Given any environment, when application logs are inspected, then no plaintext password, hash, salt, or token value appears.

---

## L2-041: JWT validation
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given any request to a protected endpoint, when the `Authorization: Bearer <token>` header is missing, malformed, signed by an untrusted key, has the wrong issuer or audience, or is expired, then the API returns HTTP 401 and no handler logic runs.
2. Given a request with a valid token, when handler logic runs, then the request's principal exposes the user id and role claims for authorization checks.

---

## L2-042: Failed sign-in rate limiting
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given 5 failed sign-in attempts for the same email within 60 seconds, when a 6th attempt arrives, then the API returns HTTP 429 with `Retry-After: 60` and no password check is performed.
2. Given 60 seconds have passed with no further attempts, when a new sign-in is attempted with the correct password, then it succeeds normally.

---

## L2-043: Audit log on failed sign-in
**Traces to:** L1-014, L1-021

**Acceptance Criteria:**
1. Given any failed sign-in attempt, when the response returns, then a row exists in the audit log with `event=SIGN_IN_FAILURE`, the attempted email, an SHA-256 fingerprint of the client IP+UA, the timestamp, and `outcome=FAILURE`.

---

## L2-044: Secrets and tokens never logged
**Traces to:** L1-014, L1-017

**Acceptance Criteria:**
1. Given any application log output (HTTP request/response logs, exception traces, custom logs), when inspected, then no JWT, refresh token, reset token, password, password hash, or connection-string secret appears verbatim.

---

## L2-045: User role permissions
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given a user with the `User` role, when they call any API to read or mutate an event, then the operation succeeds only if they are the event's host or appear on its invitee list; otherwise HTTP 403.

---

## L2-046: Admin role permissions
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given a user with the `Admin` role, when they call event-read endpoints across users, then the API authorizes the request irrespective of host/invitee status; mutating endpoints retain the host-only rule unless `Admin` is explicitly required by an admin-only endpoint.

---

## L2-047: Server-side validation via FluentValidation
**Traces to:** L1-016

**Acceptance Criteria:**
1. Given any MediatR command (e.g., `RegisterUserCommand`, `CreateEventCommand`, `UpdateEventCommand`), when it is dispatched, then a `AbstractValidator<TCommand>` runs before the handler via a `ValidationBehavior` pipeline behavior; on failure the API returns HTTP 400 `ValidationProblemDetails`.

---

## L2-048: Client surfaces field-level validation errors
**Traces to:** L1-016

**Acceptance Criteria:**
1. Given a 400 `ValidationProblemDetails` response with field names matching form inputs, when the client receives it, then each field-level message is rendered as supporting text under its respective input, the input is styled in the M3 error color, and form submission is enabled again so the user can correct.

---

## L2-049: HTTPS enforced
**Traces to:** L1-017

**Acceptance Criteria:**
1. Given the production deployment, when a client makes a request to the HTTP scheme on the API origin, then the response is a 308 redirect to the HTTPS equivalent, and HSTS with `max-age=31536000; includeSubDomains` is set on the HTTPS responses.

---

## L2-050: Sensitive data not in logs
**Traces to:** L1-017

**Acceptance Criteria:**
1. Given default request logging, when any request body containing `password`, `currentPassword`, `newPassword`, `token`, `refreshToken`, or `resetToken` is logged, then those fields are replaced by `***REDACTED***` in the log entry.

2. Given the home and event-detail screens at each breakpoint, when rendered, then the content uses single-column at XS / SM, a container at MD, and a centered max-1200px container at LG / XL.

## L2-066: Output encoding (XSS protection)
**Traces to:** L1-016

**Acceptance Criteria:**
1. Given any user-supplied value (event title, description, location, display name, full name, invitee email), when it is rendered in any Angular template, then it must be interpolated through Angular's standard binding such that any HTML, script, or attribute payload appears as literal text rather than executing as markup; `bypassSecurityTrust*` APIs shall not be used on user-supplied content.
2. Given an API response containing user-supplied content, when serialized to JSON, then it must remain a JSON string value (no HTML pre-rendering on the server), so the client controls encoding and dangerous server-side interpolation cannot occur.

---

## L2-067: Vulnerability scanning of dependencies
**Traces to:** L1-024

**Acceptance Criteria:**
1. Given the CI pipeline running on a pull request or main-branch push, when the backend job executes, then `dotnet list package --vulnerable --include-transitive` must run and any package reported at severity `High` or `Critical` shall fail the build.
2. Given the same CI pipeline, when the frontend job executes, then `npm audit --omit=dev --audit-level=high` must run and any `high` or `critical` advisory shall fail the build.
